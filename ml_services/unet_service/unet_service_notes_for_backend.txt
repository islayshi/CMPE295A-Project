U-NET SERVICE - NOTES FOR THE BACKEND TEAM (and their coding assistant)
Fight Fire With AI | from the ML team (U-Net) | written against "AI/ML Model Local Integration & LLM Implementation Guide" v2

This file lists everything about the U-Net service that is either different from the guide, not covered by it,
or still needs a decision on the backend/frontend side. Everything else follows the guide exactly.

======================================================================
1. WHAT THE SERVICE DOES (matches the guide)
======================================================================
- Files: serve.py, inference.py, native_ingestion.py, postprocessing.py, settings.py, Dockerfile (+ models/ and
  static_ca_1km.npz, the California terrain/vegetation file).
- Local: python serve.py --port 8081   or   docker run -p 8081:8081 <image>
- GET /health  -> {"status": "ok", "models_loaded": true, "models": {...}}
- POST /predict accepts:
    raw request          {"bbox": [...], "date": "...", "time_horizon": 6, "model_type": "unet", "additional_params": {...}}
    Vertex AI wrapper    {"instances": [ <raw request>, ... ]}
- Response: one GeoJSON FeatureCollection with "metadata" and features for horizons 0, 1, 3, 6
  (only horizons <= time_horizon). Each feature: Polygon, [lon, lat], closed ring, clipped to the bbox.
  properties: grid_id, fire_probability (0-1), horizon_hours, source_model ("unet"), w_unet (1.0), members (1),
  risk_label (extra).
- Native ingestion: the service fetches its own inputs (GOES-18 fire detections from NOAA's public AWS bucket,
  Open-Meteo weather, the bundled terrain/NDVI file). No .npz from the backend. Needs internet access.

======================================================================
2. DIFFERENCES / ADDITIONS YOU SHOULD KNOW ABOUT
======================================================================
2.1 Response wrapper
    - Raw request in  -> bare FeatureCollection out (as the guide says).
    - {"instances": [...]} in -> {"predictions": [FeatureCollection, ...]} out. Vertex AI REQUIRES the
      "predictions" key, so through Vertex AI you always get this wrapper. The ML adapter should unwrap
      predictions[0] when calling Vertex AI.

2.2 Extra metadata fields (all optional to use)
    metadata = {timestamp, source_model, model_version, grid_resolution_km, total_cells,     <- guide fields
                issue_time        (the hour the forecast is for, UTC)
                status            ("ok" or "no_active_fire")
                bbox, horizons,
                risk_thresholds   ({"1": {"MODERATE_RISK": x, "HIGH_RISK": y}, "3": ..., "6": ...}; differ per horizon)
                requested_model_type, time_clamped_to_latest_hour, active_fires_nearby, nearest_fire_km}

2.3 Time handling
    - "date": "YYYY-MM-DD"          -> 21:00 UTC that day (or additional_params.hour, 0-23)
    - "date": ISO timestamp         -> that hour (minutes are dropped)
    - a time in the future (e.g. today's 21:00 before it happens) -> the latest full hour;
      metadata.time_clamped_to_latest_hour = true.

2.4 model_type
    - "unet": normal.
    - "ensemble": answered with the U-Net forecast only (source_model stays "unet"), because the guide says the
      adapter combines models. metadata.requested_model_type = "ensemble".
    - "pinn" / "rl": HTTP 400 {"error": "..."} - send those to their own services.

2.5 additional_params
    - confidence_threshold: minimum fire_probability returned (default 0.05, lowest accepted 0.01).
      Burning cells (risk_label ACTIVE_FIRE) are always returned.
    - hour: see 2.3.

2.6 Errors: HTTP 400 {"error": "..."} for bad bbox/date/model_type or a bbox wider than 500 km;
    HTTP 503 if the models failed to load.

2.7 Older request format still works: {"model": "hourly", "lat": .., "lon": .., "time": ..} returns separate
    layers h1/h3/h6 (used in the Vertex AI console "Deploy & test" examples). The adapter should use the bbox format.

======================================================================
3. THINGS THAT NEED A DECISION OR CARE ON YOUR SIDE
======================================================================
3.1 Bounding box size (IMPORTANT)
    The guide says Celery computes "1 km x 1 km bounding boxes for fire anomalies". The service must clip its
    output to the bbox, so a 1 km bbox returns only the few cells inside it (tested: 16 cells for 4 horizons) and
    hides where the fire is spreading. Please pad each bbox by at least ~25 km around the fire cluster, or send one
    bbox per region. The model always works on at least a 96 km square around the bbox centre internally; the bbox
    only limits what is returned. Largest bbox: about 500 km across.

3.2 FIRMS vs GOES-18
    Your scout uses NASA FIRMS (VIIRS, 375 m pixels, a few passes a day). The U-Net needs the fire to be seen by
    GOES-18 (2 km pixels, every 10 minutes). Small fires can be in FIRMS but not in GOES-18; then the response is an
    empty FeatureCollection with metadata.status = "no_active_fire". Treat that as "no forecast available", not an error.

3.3 What the horizons contain
    - horizon 0: cells GOES-18 saw burning in the last hour before issue_time (fire_probability 1.0, ACTIVE_FIRE).
    - horizons 1/3/6: forecast cells (fire_probability = chance fire is seen there within that many hours) PLUS
      cells seen burning in the last 24 h (fire_probability 1.0, ACTIVE_FIRE), so each horizon shows the fire area.

3.4 Colour scale (frontend)
    Forecast probabilities are capped at 0.60 (higher values were over-confident in testing); burning cells are 1.0.
    A 0-1 colour ramp on fire_probability will make every forecast cell look pale. Either colour by risk_label
    (LOW_RISK / MODERATE_RISK / HIGH_RISK / ACTIVE_FIRE) or use a ramp that tops out near 0.6 and show ACTIVE_FIRE
    separately. Thresholds per horizon are in metadata.risk_thresholds.

3.5 grid_id and clipped cells (IMPORTANT for PostGIS stubbing)
    grid_id = row * 1000 + col on a fixed 1 km lattice in California Albers (EPSG:3310):
        west edge x0 = -430000 m, north edge y0 = 480000 m, row counts south, col counts east.
        cell (row, col) spans x = x0 + col*1000 .. +1000, y = y0 - (row+1)*1000 .. y0 - row*1000 (metres, EPSG:3310).
    Cells on the bbox edge are CLIPPED, so their polygon can be smaller than the real 1 km cell. If your ingestor
    stubs a new grid cell from the first polygon it sees, an edge cell could be saved with the clipped shape.
    Suggestion: build the stub geometry from grid_id with the formula above (postprocessing.grid_id_to_polygon()
    does this), or only stub from features whose polygon is a full cell.
    Note the cells are squares in EPSG:3310, so in lon/lat they are slightly rotated (not exact 0.01 deg boxes).

3.6 Response size
    Example: a 40 x 33 km bbox around the Palisades fire with all 4 horizons = 1,737 cells = about 550 KB.
    Vertex AI public endpoints reject responses over about 1.5 MB. For large bboxes or big fires, raise
    confidence_threshold, request fewer horizons, or split the bbox. Local runs have no limit.

3.7 Timing
    - First request for a past date downloads a day of GOES-18 files: roughly 10-30 s. Repeats are fast (cached).
    - Live requests ("today") are fast: the server keeps the last day of files downloaded in the background.
      For quick local tests you can turn that off with the environment variable WILDFIRE_WARM_CACHE=0.
    - Use a client timeout of at least 120 s in the adapter; on Vertex AI a first request may time out once
      (about 60 s limit) - retry after a minute.

3.8 Ports
    Local: 8081 (default in serve.py and the Dockerfile). On Vertex AI the platform sets AIP_HTTP_PORT and the
    container uses it automatically - no change needed.

3.9 Not covered by this service
    - +24 h daily model: exists but needs Earth Engine credentials; not part of the bbox contract.
    - PINN, RL, and ensemble weighting: other services / the adapter.
    - w_unet is always 1.0 here; the adapter should set its own weights when it combines models.
